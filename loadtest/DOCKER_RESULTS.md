# Docker 双实例 Redis 实测报告

测试日期：2026-09-10。此次是真实 Docker 容器测试，和 [此前本机进程测试](RESULTS.md)分别记录。原始 JSON、命令输出、容器资源采样、镜像 ID 和源文件 SHA-256 均保存在 [results/docker-20260910](results/docker-20260910)。

## 会话有序投递复测

在上述基线之后，加入了会话 `seq`、Redis Lua 序号门、节点内 CSP dispatcher 和客户端连续游标；以下测试在同一份 Compose 配置的两个后端、共享 PostgreSQL 和 Redis 上重新构建后执行。每一对私聊的两个连接固定落在不同实例，双向发送，压测端不等待 ACK。原始报告保存在运行主机的 `/tmp/gochat-ordered-optimized-*-60s.json`。

| 连接数 | 会话数 | 每连接条/秒 | 总速率 | 持续 | 写入 / ACK / 对端到达 | 对端 P50 / P95 / P99 | `ConversationSeqRegressions` |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 50 | 20 | 2,000/s | 60 s | 120,000 / 120,000 / 120,000 | 29.56 / 132.07 / 307.77 ms | 0 |
| 200 | 100 | 10 | 2,000/s | 60 s | 120,000 / 120,000 / 120,000 | 61.29 / 354.93 / 668.74 ms | 0 |

两档均无写错误、业务错误、非预期读断开、重复 ACK、重复推送或窗口内缺失。100 连接下，优化前的保序原型对端 P99 为 6.58 秒且窗口内少 234 条；移除新消息的幂等预查和私聊成员重复查询，并将发布水位合并写回后，P99 降至 307.77 ms。200 连接保持相同总吞吐时延迟上升，但仍在观察窗口内完整送达且没有会话 `seq` 回退。

## 延迟诊断：PostgreSQL WAL，而非 Redis

在 100 连接、2,000 条/秒、60 秒场景中，Redis Lua `EVALSHA` 平均为 0.074–0.099 ms，远低于端到端尾延迟。PostgreSQL 活动采样则显示大量 `COMMIT` 等待 `WALWrite` / `WALSync`；私聊会话查询的 `EXPLAIN ANALYZE` 约 0.2 ms。因此 Docker Desktop 卷上的 `fdatasync` 是本机秒级积压的主因。

仅在隔离对照环境把 PostgreSQL `synchronous_commit` 改为 `off`，保持两后端、消息速率、Redis 和保序代码不变，得到：120,000 条全部 ACK、回显和对端送达，`ConversationSeqRegressions=0`，对端 P50/P95/P99 为 **26.81 / 41.18 / 108.03 ms**。这量化了 WAL 同步提交的影响，但异步提交在主机断电时可能丢失极少量已 ACK 消息，不能作为无条件的生产默认值。

应用提供 `database.message_async_commit`（默认 `false`）作为显式选择：开启后只对聊天消息事务执行 `SET LOCAL synchronous_commit = 'off'`。同时迁移 `006` 增加 `conversation_members(user_id, conversation_id)`，避免私聊会话解析随成员总数线性扫描。

## 四实例异步提交容量复测

测试日期：2026-09-11。四个后端实例共享一个 PostgreSQL 和 Redis；每个实例的连接池上限设为 20，避免四实例合计 120 条连接超过 PostgreSQL 默认的 100 条限制。`message_async_commit = true`，只对聊天消息事务关闭 WAL 同步等待。连接以四个直连端口均匀分布，每个私聊双方落在不同实例；发送相位按连接打散。每档持续发送 60 秒，随后观察 10 秒。

低延迟验收线为：无写入/业务/读错误、ACK/自身回显/对端投递完整、无重复和会话 `seq` 乱序，且对端 P99 不超过 200ms。

| 连接数 | 总消息速率 | 成功写入 / 对端到达 | 对端 P50 / P95 / P99 | 结论 |
| ---: | ---: | ---: | ---: | --- |
| 100 | 1,900/s | 114,000 / 114,000 | 7.30 / 35.94 / 65.96 ms | 通过 |
| 100 | 2,000/s（热态复测） | 120,000 / 120,000 | 8.54 / 68.98 / 147.74 ms | 通过 |
| 200 | 1,500/s | 90,000 / 90,000 | 5.65 / 17.77 / 36.66 ms | 通过 |
| 200 | 1,800/s | 108,000 / 108,000 | 7.51 / 35.71 / 66.06 ms | 通过 |
| 200 | 1,900/s | 114,000 / 114,000 | 9.19 / 82.28 / 206.89 ms | 超过 P99 线 |
| 200 | 2,000/s | 120,000 / 120,000 | 47.18 / 2,171.48 / 3,026.60 ms | 明显排队 |

因此，在本机四实例 Docker 环境的 200ms P99 目标下，已验证的稳定工作点是 **200 个并发 WebSocket 连接、1,800 条消息/秒**。100 连接时 2,000 条/秒仍能通过；200 连接、1,900 条/秒开始越过 P99 验收线。该结果是该机器、该 Docker 存储和 60 秒持续负载下的观测，容量上线前应在目标服务器上重复长稳测试。

## 每连接每秒一条的连接容量复测

为单独衡量在线连接规模，以下四实例测试让每条 WebSocket 连接固定每秒发送 1 条消息，连接发送相位均匀打散。每档发送 60 秒、观察 10 秒，且私聊双方固定落在不同实例。验收条件仍为：对端 P99 不超过 200ms、无错误、无窗口内缺失、无重复和无会话 `seq` 乱序。

| 连接数 | 每实例连接数 | 总消息速率 | 成功写入 / 对端到达 | 对端 P50 / P95 / P99 | 结论 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 200 | 50 | 200/s | 12,000 / 12,000 | 2.86 / 3.59 / 4.36 ms | 通过 |
| 500 | 125 | 500/s | 30,000 / 30,000 | 3.24 / 4.57 / 6.59 ms | 通过 |
| 1,000 | 250 | 1,000/s | 60,000 / 60,000 | 4.18 / 6.66 / 10.73 ms | 通过 |
| 1,500 | 375 | 1,500/s | 90,000 / 90,000 | 5.86 / 23.85 / 40.78 ms | 通过 |
| 1,800 | 450 | 1,800/s | 108,000 / 108,000 | 12.18 / 58.05 / 101.16 ms | 通过 |
| 1,900 | 475 | 1,900/s | 114,000 / 114,000 | 20.84 / 78.93 / 144.11 ms | 通过 |
| 2,000 | 500 | 2,000/s | 120,000 / 120,000 | 40.79 / 184.20 / 343.85 ms | 超过 P99 线 |
| 5,000 | 1,250 | 5,000/s | 299,791 / 157,254 | 18,341.71 / 35,986.63 / 39,977.83 ms | 写入/读断开与积压 |

在此环境及验收线下，已验证的低延迟连接容量为 **1,900 个并发 WebSocket 连接**，即四个实例各 475 个连接、总 1,900 条/秒。2,000 连接时消息仍全部落库和投递，但 P99 超过目标；5,000 连接出现积压和连接读写错误，因此不应作为可用容量。该数字是单机 Docker 上的 60 秒观测，不是线上服务器的容量承诺。

## PostgreSQL 发布水位解耦复测

测试日期：2026-09-15。为解释 2,000 连接附近的延迟突增，隔离环境额外启用了 `pg_stat_statements` 和 `track_io_timing`。同为四实例、每连接每秒 1 条、60 秒发送和 10 秒观察，未优化基线的对端 P99 为 **11,395.74ms**。统计发现正常异步水位写来不及推进时，四个实例每 2 秒扫描 `last_seq > last_published_seq`，把尚在正常发布中的会话误判为故障：约 5.8 万次恢复事务重复读取消息并更新与序号分配共用的 `conversations` 行，形成锁竞争和恢复放大。

最终方案把 `last_published_seq` 的运行时水位移到独立的 `conversation_publish_watermarks` 表，水位刷盘使用 4 个有界 worker，并且恢复扫描只选择“第一条未发布消息已滞留 30 秒”的会话。Redis 发布失败仍立即入队恢复；正常发布后的水位写失败只重试水位，不立即回放已经进入 Redis 的消息。迁移保留 `conversations.last_published_seq` 以兼容既有迁移历史，新代码不再在消息序号热行上写发布水位。

| 连接数 | 总速率 | 写入 / ACK / 对端到达 | 对端 P50 / P95 / P99 | 恢复消息读取 | 乱序 / 重复 | 结论 |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 2,000（剖析基线） | 2,000/s | 119,997 / 117,847 / 116,688 | — / — / 11,395.74 ms | 58,051 | 0 / 0 | 恢复放大，失败 |
| 2,000（仅 4 worker） | 2,000/s | 120,000 / 119,864 / 119,817 | — / — / 6,606.95 ms | 约 18,000 | 0 / 0 | 有改善，仍有积压 |
| 2,000（独立水位表） | 2,000/s | 120,000 / 120,000 / 120,000 | 64.44 / 389.71 / 771.16 ms | 0 | 0 / 0 | 完整送达，超过 200ms 线 |
| 1,900（独立水位表） | 1,900/s | 114,000 / 114,000 / 114,000 | 29.69 / 186.20 / 339.55 ms | 0 | 0 / 0 | 完整送达，超过本轮 200ms 线 |

这组带 SQL 统计的结果与 2026-09-11 未启用统计时的数据不能绝对横向比较；它用于同一时段、同一机器上的相对验证。最终 2,000 连接档没有写错误、读错误、窗口内缺失、重复或三类顺序回退，数据库水位最终与 `last_seq` 完全一致。P99 相对本轮剖析基线下降约 **93.2%**，但仍未达到 200ms 目标，因此当前保守容量结论仍采用此前已验证的 1,900 连接档，生产容量需在目标服务器重新测量。

## 环境

- Docker Desktop 29.0.1，16 个逻辑 CPU，可用内存约 15.51 GiB；4 个专用容器，无单容器 CPU/内存硬配额。
- 两个当前工作区代码构建的 Go 后端；PostgreSQL 16.14（独立命名数据卷）、Redis 7.4.9；每后端数据库连接池上限 30。
- Redis `PUBSUB NUMSUB ws:events` 返回 **2**。连接交替固定到两个后端端口 18081、18082，每个私聊对的发送者位于不同容器。所有会话均跨实例。
- 压测客户端运行在 WSL，直连 Docker 发布端口；没有经过 Nginx。用户原有容器保持运行，可能存在其他负载干扰。
- 应用日志 info，HTTP 限流仅在测试配置关闭。开始时为新测试数据库，随后逐档累积测试数据；各档之间等待 5 秒，没有逐档重建数据库。
- 账号准备与建连接不计入消息测量。双向私聊，不等待 ACK，不重试、不重连、不补拉；每条消息同时观察 ACK、对端推送和自身回显。

## 60 秒持续负载

发送结束后再观察 5 秒。

| 连接数 | 每连接条/秒 | 发送条数 | 对端 P50 / ms | 对端 P99 / ms | 截止时未到达 | 会话 ID 回退 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 20 | 120,000 | 28.66 | 94.28 | 0 | 21,697 |
| 1000 | 1 | 60,000 | 958.98 | 19401.56 | 0 | 11,045 |

100 连接、每连接每秒 20 条这一档，成功写入速率约 2001.6 条/秒；12 万条对端推送均到达，P99 为 94.28 ms。该数值是本次单机共享资源环境的观测，不是最大处理能力或线上 SLA。

1000 连接的低频档共 60,000 条全部到达，P50 为 958.98 ms，P99 为 19,401.56 ms，最大约 20.46 秒；连接维持成功并不代表低延迟。

1000 连接的低频档用于把连接规模和消息处理速率分开。所有发送者按相同时间基准发送，因此每秒会形成一批约 1000 条消息，并非均匀分散的流量；延迟应结合这一突发特征理解。

## 顺序与完整性

全部 7 档中，写错误、业务错误、非预期读断开、重复 ACK、重复推送、同一发送者序号回退均为 **0**。

**各档均观察到了同一会话内消息 ID 到达顺序回退。** 单个发送者序号有序，并不等于多个发送者并发时会话按数据库 ID 全局有序。Redis 只按发布顺序投递；事务、查询接收者、发布对端推送与发布自身回显可以在不同实例之间交错。前端排序也不能证明原始推送有序。各 JSON 的 `OrderExamples` 保留具体样例。

## 复现

在仓库根目录执行：

```bash
docker compose -p gochat-bench -f loadtest/compose.yml up --build -d --wait
go build -o /tmp/gochat-loadtest ./loadtest
python loadtest/run-docker.py --output loadtest/results/docker-new-run
docker compose -p gochat-bench -f loadtest/compose.yml down
```

输出目录应尚不存在。`down` 保留专用数据库卷，已有数据会影响后续复测；本次初始空库状态见容器启动记录。工具口径与限制见 [README](README.md)。测试完成后已停止本次创建的专用容器，保留数据卷和报告，用户原有服务未修改。
