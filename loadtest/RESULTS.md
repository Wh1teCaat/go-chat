# 双实例实测报告

后续已完成真正的 Docker 容器压测，见 [Docker 双实例报告](DOCKER_RESULTS.md)。本页保留之前本机独立进程的数据。

测试日期：2026-09-10。原始数据保存在 [results](results/)，指标定义与复现命令见 [README](README.md)。

## 环境与负载

- WSL2 / Linux，Intel Core i7-10875H，16 个逻辑 CPU，约 15.5 GiB 内存；压测客户端、两个真实 Go 后端进程、PostgreSQL 16.15 和 Redis 7.0.15 在同一台开发机运行，无 CPU/内存容器配额。
- 两个后端分别监听 18081、18082，直连并交替分配连接，每一对会话均跨实例；没有经过 nginx。本机缺少 Docker，因此实际使用下载到 `/tmp` 的服务端二进制和独立 PostgreSQL 数据目录，没有使用模拟数据库或模拟 Redis。
- 每实例 PostgreSQL 连接池上限 30，HTTP 限流在专用测试配置中关闭，应用日志等级 info。保留现有业务代码和 GORM 日志行为。
- 每对用户建立独立私聊会话，双方同时发送；每个连接目标 20 条/秒，200 条消息，发送阶段约 10 秒，随后等待 5 秒。每条消息产生 ACK、对端推送和自身回显。账号及会话准备不计时。
- 各档按顺序运行，共享独立测试数据库，未在档位之间清空数据；没有自动重试、重连或补拉。20 连接档期间曾并行尝试运行仓库测试，因此该档也可能受到额外主机负载干扰。

所有档位的客户端写错误、业务错误、非预期读断开、重复 ACK、重复推送和同一发送者序号回退均为 0。高压档延迟分位数仅覆盖窗口内收到的消息，不能代表全部发送消息。

100 连接档发送 20,000 条，对端全部收到，P99 为 54.4 ms。200 连接档虽在额外 5 秒观察窗口内收齐 40,000 条，但 P99 已达 4.61 秒，说明此发送速率下出现明显积压。500、1000 连接档分别有 62.8%、91.5% 的消息在截止时未收到对端推送；写入 socket 成功不能用作服务端处理成功的证明，也不能把窗口内未到达直接写成永久丢失。

这些结果不支持“1000 并发用户低延迟稳定收发”的表述。连接数量必须与每连接发消息频率、观察时长和错误/延迟指标同时报告。

## 乱序结论

**确实存在会话内消息 ID 到达乱序；本次样本未观察到单个发送者的发送序号乱序。**

20 连接档的一个原始样例：同一接收连接先看到了消息 ID 40，之后收到 ID 24（发送者 0 的第 2 条消息）。该回退是在同一个私聊会话内比较，包含自身消息回显和对端推送，不是把不同会话混在一起排序造成的。完整样例在各 JSON 的 `OrderExamples` 字段中。

代码路径是：分配消息 ID / 事务提交 → 查询接收者 → 发布对端推送 → 发布发送者回显。不同连接/实例可以交错执行这些步骤，因此 Redis 的发布顺序不等于消息 ID 顺序。消息 ID 也不应被视为并发事务严格的提交顺序。已修正设计文档中“单频道下消息顺序与落库顺序一致”的表述。

前端按 ID 排序能调整展示顺序，但不能将原始推送变为全局有序。若以后需要严格会话顺序，应另外设计会话序号、串行发布/分区消费与客户端缺口处理；本次未修改消息链路。

## 资源与测量边界

每档 `*-resources.json` 保存每秒采样的 RSS 峰值，顺序为 PostgreSQL 主进程、Redis、后端 1、后端 2、压测进程。**PostgreSQL 值只包含主进程，不包含其工作进程，不能当数据库总内存。** 未采集 CPU 利用率、SQL 时延分布或磁盘 I/O，因此无法仅据此次结果确定瓶颈所在。GORM 当前会记录幂等查询的正常未命中，属于后续可测量的日志开销来源。

这是单机共享资源下的观测，并非生产 SLA 或最大容量认证。计时包含压测客户端调度和本地网络开销，负载按固定时间计划同步发出，具有批次突发特点；数据库逐档变大、缓存状态和其他开发机负载都会影响结果。工具的内存占用随消息数增长。
