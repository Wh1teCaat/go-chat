# 阶段 3：事件总线从 Redis Pub/Sub 迁移到 Kafka

## 动因

阶段 1 用 Redis Pub/Sub 解决了"跨实例路由"，但它有两个结构性天花板：

1. **fire-and-forget**：没有持久化、没有位点。gateway 掉线/重启期间的事件直接蒸发，只能靠客户端补拉兜底；事件本身不可重放、不可审计。
2. **单用途**：订阅者只有 gateway 推送这一类。要加离线推送（用户不在线时发 APNs/厂商通道）、消息轨迹/审计，这些消费者和实时推送的消费节奏完全不同，Pub/Sub 里没法互不干扰地共存——"新用途不改老链路"做不到。

Kafka 的持久化日志 + 独立消费组正面解决这两点。这不是"为了简历堆组件"：判断标准是**是否出现了第二类消费者的需求**，离线推送就是聊天产品绕不开的那一类。

## 设计

```text
chat-logic ──WriteMessages(key=conv:<id>)──▶ Kafka topic chat.events（8 分区）
                                                 │ 每实例独立消费组（广播语义）
                             ┌───────────────────┼───────────────────┐
                     gateway-1 消费组      gateway-2 消费组      （未来）离线推送/轨迹消费组
                     投递本地在线用户      投递本地在线用户
```

- **顺序**：`Bus.Publish` 增加了顺序域键参数——会话事件用 `conv:<会话ID>`，好友通知 `user:<id>`，群通知 `group:<id>`。Hash balancer 按 key 选分区，**同会话的消息和已读回执落同一分区、分区内严格有序**；不同会话互不阻塞（并行度 = 分区数）。这是从 Redis 单通道"全局串行"到"按顺序域并行"的升级。
- **广播语义**：Kafka 消费组内是分摊（一条消息只给组内一个成员），而推送需要每个 gateway 都收到全量事件再各自过滤本地在线用户——所以**每个 gateway 实例每次启动一个全新消费组**（组名 `chat-gateway-<hostname>-<随机后缀>`）。"每次启动新组"是有意的：若组名稳定复用，latest 位点只在首次生效，重启会从旧位点重放宕机期积压（好友/群通知没有去重键，会产生可见重复）；同机多进程还会因组名相同落入分摊语义、各丢一半事件。空闲旧组由 broker 按 `offsets.retention.minutes=1440` 自动清理。
- **启动就绪探测**：消费组 join/rebalance 需要数秒，而 latest 位点在分配时才解析——若 gateway 先接客再等消费组就绪，这个窗口内发布的事件会被整体跳过且在线用户无从补拉。`NewKafkaBus` 用探针事件自证"发布→消费"链路端到端打通后才返回（与 RedisBus 等订阅确认的启动语义对齐），main 在此之后才开始 ListenAndServe。
- **投递语义**：at-least-once。重复投递的兜底是阶段 0 就存在的客户端幂等（按消息 ID / clientMsgID 去重），服务端不需要 exactly-once 的复杂度——这是"端到端幂等让中间件选型变简单"的典型例子。
- **新消费组从 latest 加入**：gateway 重启期间的事件不重放（重放给刚重连的客户端反而重复），掉线补偿仍走 `afterMessageID` 增量补拉。可达性依然锚定在数据库，总线只负责实时性——这个边界从阶段 1 起没有变过。
- **降级**：`kafka.enabled=false` 时 logic/gateway 自动退回 Redis Pub/Sub（阶段 2 形态）；Kafka 短暂故障时发布端降级本地直投并告警，与限流 fail-open 同一取舍。

## Pub/Sub vs Kafka（面试速查）

| 维度 | Redis Pub/Sub | Kafka |
|---|---|---|
| 持久化 | 无，掉线即丢 | 日志持久化，按 retention 保留 |
| 消费位点 | 无 | 每消费组独立位点，可重放 |
| 多消费者 | 所有订阅者同构 | 消费组互不干扰，新用途零侵入 |
| 顺序 | 单通道全局有序 | 分区内有序，按 key 划分顺序域并行 |
| 延迟 | 亚毫秒 | 毫秒级（本项目 BatchTimeout 5ms） |
| 运维 | 极轻 | 重（本项目 KRaft 单节点起步） |

选型结论：需要"事件可重放 + 多消费组"之前，Pub/Sub 是对的；出现之后，Kafka 是对的。两个阶段都保留在代码里（配置切换），本身就是答案。

## 客户端库选型

`segmentio/kafka-go`：纯 Go（无 cgo，交叉编译进 alpine 镜像无负担）、Reader/Writer 抽象直接对应本项目的消费/发布两种角色。sarama 认知度更高但 API 冗长，franz-go 性能最好但社区面较窄；本项目吞吐远未到需要压榨客户端性能的量级，选可读性。

## 遗留 / 下一步

- **落库与发布的原子性**：当前是"DB 事务提交 → 发 Kafka"两步，中间进程崩溃会出现"已落库但未发布"（在线用户暂时看不到，补拉可见）。严格解法是 **transactional outbox**（事件先写库内 outbox 表，同事务提交，再由中继/CDC 搬运到 Kafka）——面试高频考点，当前规模下补拉兜底已够，列为 logic 拆分 message 服务时的配套改造。
- 离线推送消费者：挂一个新消费组消费 `chat.events`，对不在线（presence 查不到）的接收者调推送通道。事件流已经就绪，这一步只增不改。
- **扩分区会破坏同 key 的顺序**：Hash 分区的 key→分区映射依赖分区总数，扩分区瞬间同会话的新旧事件会跨分区。需要扩容时要么停写窗口，要么建新 topic 双写迁移。
- 单节点 KRaft 无副本；生产至少 3 broker + replication.factor=3 + acks=all，且发布端当前 `RequireOne + MaxAttempts=2 + 3s 上限`是为"快速失败、降级补拉"调的参数，生产要按丢失容忍度重调。
